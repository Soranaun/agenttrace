# AgentTrace 后续规划

> 以下全部为提交后的拟议工作，不是当前已实现能力，也不是固定交付承诺。当前赛事交付冻结产品功能，以已通过验收的 MVP 为准。

## 阶段一：格式和回归稳定

目标是让现有功能可以持续复查，优先于扩大功能范围。

- 整理 schema_version=1 的兼容规则、稳定步骤 ID 和重试命名示例。
- 根据实际问题补充回归用例，考虑在公开仓库配置自动化 CI。
- 明确维护负责人、问题分流与版本记录流程；在用户确认后发布可定位到提交的版本。

验收条件：现有模拟文件仍可解析，全部测试通过，格式变更有迁移说明，发布记录能够关联代码与验收材料。目前尚未建立自动化 CI 或正式发布流程。

## 阶段二：真实任务小规模接入

目标是验证记录器在模拟以外的使用价值。

- 优先选择一项经授权的课程或个人 Python 工具链任务，显式接入现有记录器。
- 在共享前人工移除敏感信息，检查输入输出是否能完整序列化。
- 收集接入步骤、失败样例和使用反馈，再决定是否需要框架适配器。

验收条件：获得可公开或可脱敏复查的真实任务记录，能完成导入、回放和修改前后对比；记录验证环境和使用者反馈。没有试点数据前不宣称生产落地、准确率或调试效率提升。

## 阶段三：依据反馈决定扩展

可讨论方向包括批量诊断、运行分组、显式重试表示和框架适配。并发追踪、鉴权、自动脱敏及多用户服务涉及额外语义和安全要求，需先形成需求与设计，再决定是否实施。

验收条件应在选定任务后单独制定；至少包括兼容性、回归测试和可复现示例。不预先承诺自动根因分析、自动修复或付费模型接入。

## 维护原则与现实约束

保持可离线查看记录、优先修复可复现问题、避免将模拟结果包装为业务成绩。贡献流程见 [CONTRIBUTING](../CONTRIBUTING.md)。目前没有已确认的长期人力、经费、服务等级或维护响应时间；团队应在后续使用反馈基础上确认承担范围。
